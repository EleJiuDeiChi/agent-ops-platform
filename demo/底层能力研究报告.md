## 2. 许可与合规结论

1Panel 是 GPLv3。可以研究架构和实现思路；如果直接复制、修改并分发其代码，需要遵守 GPLv3 的传染性开源义务。证据：`demo/1Panel/LICENSE`、`demo/1Panel/README.md`。

宝塔面板不是常规宽松开源协议。其 `license.txt` 写明允许以自用为目的修改公开源代码，但限制发行、出租、出售、传播修改后的源代码或衍生产品，并限制绕过授权机制。因此本项目只能做能力研究和产品/架构借鉴，不应直接复制宝塔业务代码。证据：`demo/BaoTa/license.txt` 第 10 节。

## 3. 一句话结论

1Panel 更适合作为本项目底层架构参考：控制面与执行面分离、Go agent、typed API、统一异步任务、Docker/Compose/AppStore/AI runtime 都更接近现代 AI 运维平台。

宝塔更适合作为能力清单与运维脚本库参考：覆盖面非常广，包含网站、数据库、文件、终端、计划任务、插件、备份、SSL、系统安全、日志、Docker、项目运行时等大量经验，但底层形态偏 Python Flask 单体 + shell 命令 + 插件二进制，直接照搬会带来安全、可维护性和许可风险。

## 4. 能力矩阵

| 能力域 | 1Panel | 宝塔面板 | 对本项目的判断 |
| --- | --- | --- | --- |
| 控制面/执行面 | `core` + `agent` 双 Go 模块；core 可代理本地 agent；agent 有 master unix socket 和 node TLS 模式 | Flask 单体 `BTPanel` 直接调 `class`/`mod`/`script` | 采用 1Panel 式控制面 + agent；不要做单体 root shell 面板 |
| API 路由 | Gin 路由分域：容器、主机、网站、数据库、AI、设置、日志等 | Flask 路由集中在 `BTPanel/__init__.py`，大量动态 controller 路由 | API 要显式、typed、可审计；动态路由只做插件隔离层 |
| 异步任务 | `agent/app/task` 统一 task/subtask/log/status/cancel | `panelTask.bt_task` + SQLite `task_list` + `BT-Task` 执行 | 采用统一任务模型，任务日志和状态必须成为一等资源 |
| 命令执行 | `agent/utils/cmd` 包装 timeout、pipe、sudo、task log | `public.ExecShell`、`task.py exec_shell`、大量 `os.system` | 必须封装命令执行器，做 allowlist、timeout、stdout/stderr、审计、取消 |

| 容器/Docker | Docker SDK + compose-go + docker CLI；容器、镜像、网络、卷、Compose、daemon.json | Python Docker SDK + docker-compose CLI；支持容器、Compose、镜像仓库、GPU | 优先 1Panel 的 SDK/typed service 模式；借鉴宝塔命令入口的危险命令过滤 |
| 网站/Nginx/SSL | OpenResty/Nginx 配置、站点、域名、反代、重写、HTTPS、ACME、DNS、负载均衡 | Nginx/Apache/OpenLiteSpeed vhost 模板、重写模板、SSL、商业证书、反代、目录权限 | 可先做 Nginx/OpenResty 子集，配置生成必须可 diff、可回滚 |
| 数据库 | MySQL/PostgreSQL/Redis/MongoDB，本地和远程，备份恢复 | MySQL/MariaDB 为主，兼有 PostgreSQL/MongoDB/Redis/SQLite/SQL Server 模块 | 先实现连接检测、账号/权限、备份恢复、慢查询/状态，不急于全库种类 |
| 文件管理 | 文件 API、压缩解压、分享、历史、回收站、上传下载 | 文件管理模块非常成熟，包含压缩、回收站、上传下载、搜索、权限 | 文件能力要强约束路径边界，避免任意 root 文件写入 |
| 防火墙/安全 | firewalld/ufw/iptables、SSH、fail2ban、进程、ClamAV | firewalld/iptables/ufw、安全告警、SSH 安全、恶意文件检测、WAF 相关入口 | 本项目应先做诊断和建议，再做带审批的修改 |
| 监控/进程 | gopsutil、GPU/XPU、process ws、top CPU/mem、历史监控 | psutil、网络/磁盘/进程、站点日志、告警推送 | 监控数据模型要独立于 UI，便于 Agent 推理 |

## 5. 1Panel 底层架构拆解

### 5.1 代码形态

1Panel 当前主线是 Go + Vue。

- `demo/1Panel/core`：控制面核心，Gin API、认证、session、迁移、反向代理、全局设置。
- `demo/1Panel/agent`：实际节点执行面，负责主机、容器、网站、数据库、AI、备份、任务等操作。
- `demo/1Panel/frontend`：Vue 3 + Element Plus 前端。

核心依赖能说明底层能力边界：

- `core/go.mod`：Gin、Gorm/SQLite、WebAuthn、cmux、WebSocket、cron、sftp、captcha、session/auth 相关。
- `agent/go.mod`：Docker SDK、compose-go、lego ACME、gopsutil、MySQL/PostgreSQL/Redis/MongoDB client、S3/OSS/COS/MinIO/OneDrive/Qiniu/Upyun、WebSocket、cron。

### 5.2 控制面与 agent

`core/server/server.go` 初始化配置、日志、DB、迁移、i18n、validator、geo、cron、session、hook、proxy，再挂载 Gin router。

`agent/server/server.go` 初始化配置、目录、日志、DB、迁移、cache、app、cron、hook、firewall，再挂载 agent router。agent 有两种运行形态：

- master 模式：监听 `/etc/1panel/agent.sock`，权限强约束为 `0700` 目录和 `0600` socket。
- node 模式：监听 HTTPS，并用 `tls.RequireAndVerifyClientCert` 做客户端证书校验。

这对本项目很关键：Agent 运维平台不能只做本地 Web 后端直接执行命令，应该有一个明确的节点执行 agent，控制面只发任务、收事件、做代理。

### 5.3 路由与能力域

1Panel 的 agent 路由拆得比较清晰：

- 容器：`agent/router/ro_container.go`
- 网站：`agent/router/ro_website.go`
- 数据库：`agent/router/ro_database.go`
- 主机/防火墙/SSH/终端/磁盘：`agent/router/ro_host.go`
- AI/Ollama/GPU/MCP/Agent/TensorRT：`agent/router/ro_ai.go`
- 运行时：`agent/router/ro_runtime.go`
- 备份：`agent/router/backup.go`
- 进程：`agent/router/ro_process.go`
- 日志/任务：`agent/router/ro_log.go`

这些路由背后对应 `agent/app/service/*.go`，不是前端直接拼 shell。这是值得学习的服务边界。

### 5.4 任务模型

`agent/app/task/task.go` 定义统一任务：

- task 有 `TaskID`、`Name`、`Operate`、`Scope`、`ResourceID`、`Status`、`LogFile`。
- 支持 `SubTask`、retry、timeout、rollback、ignore error。
- 用 `global.TaskCtxMap` 保存取消函数。

本项目应直接采用类似模型：所有耗时/高危操作都必须进入任务系统，而不是同步 HTTP 请求里执行。

### 5.5 命令执行与系统能力

1Panel 封装在 `agent/utils/cmd/cmdx.go`：

- 支持 timeout、context、工作目录、环境变量、stdout/stderr、pipe、script file。
- Docker/数据库/压缩/防火墙等上层服务通过这个封装或 SDK 操作。

本项目应进一步加强：

- 命令 allowlist/denylist。
- 参数结构化，避免拼 shell。
- 高危命令审批。
- stdout/stderr 实时事件化。
- 每个命令绑定 operator、reason、resource、task_id。

### 5.6 AI 原生能力

1Panel 的 AI 已经不是装饰页面，而是底层运维能力：

- Ollama 模型管理：`agent/app/service/ai.go`
- MCP server：`agent/app/service/mcp_server.go`
- TensorRT-LLM：`agent/app/service/tensorrt_llm.go`
- GPU/XPU 监控：`agent/router/ro_ai.go`、`agent/utils/ai_tools`
- Agent 账号、模型、技能、渠道、网站绑定：`agent/app/service/agents*.go`
- 终端 AI：`agent/utils/terminal/ai_*`

本项目如果要做“AI 原生运维面板”，应该把 AI 放在执行链路中：诊断计划、工具选择、命令建议、审批、执行、结果解释，而不是仅做聊天入口。

## 6. 宝塔面板底层架构拆解

### 6.1 代码形态

宝塔是 Python Flask 单体 + 大量系统脚本 + 插件体系。

- `demo/BaoTa/runserver.py`：读取 `data/port.pl`，启动 Flask app。
- `demo/BaoTa/BTPanel/__init__.py`：Flask app、session、鉴权、路由、WebSocket、动态 controller。
- `demo/BaoTa/class`：核心业务类，网站、数据库、文件、计划任务、防火墙、SSL、Docker、终端、插件、监控等。
- `demo/BaoTa/mod`：新式模块化能力，项目、Docker、Agent、备份恢复、节点、代理、SSL 等。
- `demo/BaoTa/script`：大量后台运维脚本。
- `demo/BaoTa/vhost`、`demo/BaoTa/rewrite`：Web 服务配置模板和重写规则。

### 6.2 Flask 路由与动态 controller

`BTPanel/__init__.py` 路由覆盖面很广：

- `/site`、`/database`、`/ftp`、`/files`、`/crontab`、`/firewall`、`/ssl`、`/docker`、`/soft`、`/config`、`/system`、`/logs`。
- WebSocket：`/ws_panel`、`/ws_home`、`/ws_project`、`/ws_files`、`/sock_shell`、`/webssh`、`/pyenv_webssh`、`/ws_mod`。
- 动态模块路由：`/<index>/<mod_name>/<def_name>`、`/mod/<name>/<sub_name>/<fun>`、`/database/<mod_name>/<def_name>`、`/safe/<mod_name>/<def_name>`。

这种能力覆盖强，但安全边界依赖 controller 约定和全局过滤。本项目不应复制这种大而动态的单体路由。

### 6.3 命令执行与任务队列

宝塔底层大量能力围绕 shell：

- `class/public.py` 的 `ExecShell` 是通用命令执行入口。
- `task.py` 有 `exec_shell`，将输出重定向到 `/tmp/panelExec.log`。
- `class/panelTask.py` 维护 SQLite `task_list`，任务类型包含 shell、下载、解压、压缩、备份数据库、导入数据库、备份网站、文件复制、回收站清空等。
- `panelTask.create_task` 会写 `/dev/shm/bt_task_now.pl`，并启动 `/www/server/panel/BT-Task`。

借鉴点：宝塔把“文件下载/压缩/备份/恢复/安装软件”都纳入任务队列，前端通过日志看进度。

风险点：大量命令仍是字符串拼接和 root 级系统命令。本项目应该用 typed command runner 和工具级权限模型替代。

### 6.4 网站与 Web 服务

宝塔的网站能力非常完整：

- `class/panelSite.py`：站点创建、删除、SSL、PHP 版本、备份等。
- `vhost/template/nginx`、`vhost/template/apache`：Nginx/Apache 站点模板。
- `rewrite/nginx`、`rewrite/apache`：WordPress、Discuz、Laravel、ThinkPHP 等重写模板。
- `mod/base/web_conf`：反代、跳转、防盗链、CORS、Real IP、访问控制、日志、Gzip、Nginx cache 等配置模块。

本项目可以借鉴“配置模板 + 参数化生成 + reload + 回滚”的模式，但必须加：

- 生成前 diff 预览。
- Nginx config test。
- 原配置备份。
- reload 失败自动回滚。
- 所有变更写审计日志。

### 6.5 Docker 与运行时

宝塔 Docker 能力分两层：

- 老模型：`class/btdockerModel/*`，例如 `containerModel.py`、`composeModel.py`、`dockerBase.py`。
- 新项目模块：`mod/project/docker/*`，包含 app、apphub、compose、runtime、sites、gpu、proxy。

实现方式混合了 Python Docker SDK 和 `docker-compose` CLI。`dockerBase.run_cmd`、`containerModel.run_cmd` 做了危险命令和危险符号过滤，只允许 `docker run`/`docker pull` 这类入口。

借鉴点：命令入口必须有风险过滤；Docker app/site/runtime 分域有产品价值。

风险点：仅靠字符串过滤不够；应该把 Docker 操作做成结构化 API。

### 6.6 终端与 SSH

`class/ssh_terminal.py` 覆盖：

- Paramiko SSH 连接。
- 本地 shell/pty。
- WebSocket 读写。
- SSH 登录记录与可选录像。
- 自动解析 SSH 端口。
- 自动创建/选择 SSH key。
- `safe_bt_shell.sh` 安全 shell 初始化。

这是很值得借鉴的能力，但本项目更应该把终端变成 AI 运维的“受控执行面”：

- 默认进入受控 shell。
- 高危命令拦截。
- AI 命令建议只填入输入框，不自动执行。
- 所有会话录制和审计。

### 6.7 插件与扩展

宝塔插件体系主要由 `class/panelPlugin.py`、`pluginAuth.py`、`plugin_tool.py`、`PluginLoader.*.so`、`/plugin` 目录和远端 API 组成。插件市场、安装、修复、升级、依赖检测、云端授权都已经做得很完整。

本项目可以学习“能力可插拔”，但不应加载不透明二进制插件。建议做：

- 工具插件 manifest。
- 输入输出 JSON schema。
- 最小权限 capability 声明。
- sandbox/容器化执行。
- 插件安装前静态检查。
- 插件调用审计。

### 6.8 AI 与诊断

宝塔已经出现 AI/Agent 相关模块：

- `mod/project/agent/chat_client/*`
- `mod/project/agent/prompts/*.md`
- `mod/project/agent/skill_agents/*.md`
- `class/projectModel/aiModel.py`
- `vhost/template/nginx/ai_http.conf`

这说明传统面板也在往 AI 运维诊断靠。但宝塔的 AI 更像嵌入既有面板；本项目应反过来设计：AI 诊断流是主入口，传统运维操作是工具。

## 7. 对本项目的设计建议

### 7.1 底层架构

建议采用：

```text
Web UI / AI Console
        |
Backend Control Plane
        |
Task + Audit + Approval + Event Stream
        |
Node Agent(s)
        |
Host / Docker / Nginx / DB / Files / SSH / Metrics
```

关键原则：

- 控制面不直接执行 root 命令。
- agent 按 capability 暴露工具。
- 每个工具有 schema、risk_level、dry_run、rollback、audit fields。
- 大操作全部进入任务队列。
- 事件流面向 UI 和 AI 同时输出。

### 7.2 优先实现的底层能力

第一优先级：

- 节点注册与 agent heartbeat。
- 命令执行器：timeout、工作目录、env、stdout/stderr streaming、取消、审计。
- 统一任务模型：pending/running/succeeded/failed/cancelled，substeps，日志。
- 主机基础信息：CPU、内存、磁盘、网络、进程、服务状态。
- SSH/终端 WebSocket：只读审计、会话录制、高危命令拦截。
- 文件读取/上传/下载/权限/压缩解压，限制根目录和敏感路径。

第二优先级：

- Docker 容器/镜像/网络/卷/Compose。
- Nginx 站点和反代。
- SSL/ACME/DNS 验证。
- MySQL/PostgreSQL/Redis 的连接、账号、备份恢复。
- 防火墙和 SSH 安全策略。

第三优先级：

- 应用商店。
- 多节点。
- 快照/整机备份。
- MCP/Agent 插件市场。
- GPU/本地模型运行时。

### 7.3 UI 与产品形态

本项目已有规则要求后台页面优先 Ant Design，AI 对话页面优先 Ant Design X。结合这次研究，建议 UI 不是复刻面板菜单，而是三层：

- 概览：主机状态、风险、最近任务、待审批动作。
- AI 诊断台：对话、诊断计划、工具调用链、事件流、结果报告。
- 专业工具区：服务器、容器、网站、数据库、文件、终端、审计、报告。

### 7.4 不建议照搬的点

- 不要复制宝塔源码或插件体系：许可和不透明二进制 loader 风险都高。
- 不要把 shell 字符串拼接散落在业务代码里。
- 不要让 HTTP 请求同步执行高危命令。
- 不要用动态 controller 作为核心 API。
- 不要先做大而全的菜单；应先做 AI 运维闭环：诊断、计划、审批、执行、验证、报告。

## 8. 可直接转化为本项目 backlog 的任务

1. `agent_capabilities` 表：记录 agent 支持的工具、版本、风险等级、输入输出 schema。
2. `ops_tasks` 表：任务、子任务、资源、状态、日志路径、审计字段、取消 token。
3. `ops_events` 表或流：命令输出、工具状态、诊断步骤、审批事件。
4. `command_runner`：结构化命令执行，禁止裸 shell 拼接；提供 shell 兼容层但必须标记高风险。
5. `approval_policy`：按工具和参数决定是否需要审批。
6. `agent_transport`：本地 unix socket + 远程 mTLS HTTPS。
7. `terminal_session`：WebSocket、录制、命令风险拦截、审计。
8. `docker_adapter`：先做 Docker SDK 查询和只读操作，再开放 create/start/stop。
9. `nginx_adapter`：站点配置生成、diff、test、reload、rollback。
10. `diagnosis_console`：Ant Design X 的 Bubble.List、Sender、ThoughtChain、Actions，用事件流展示 AI 工具调用。

## 9. 最终判断

如果目标是做“服务器运维面板”，宝塔的能力覆盖是最完整的参考清单。

如果目标是做“AI 原生服务器运维平台”，1Panel 的底层架构更接近正确方向：agent 化、任务化、容器化、API 化，并且已经把 AI/Agent/MCP/GPU 放进底层能力域。
