# R0 release and supply-chain evidence contract

Evidence is immutable only when bound to a source commit and image digest.
Local output and mutable image tags are diagnostic evidence, not release proof.

## Pull request and branch artifact

`.github/workflows/r0-ci.yml` builds both images and uploads
`r0-supply-chain-<run_id>-<attempt>` containing:

- Docker Engine and Compose versions from that runner;
- full `docker image inspect` JSON for both local CI images;
- SPDX JSON SBOMs generated by Syft 1.46.0;
- Trivy 0.72.0 JSON scans for all HIGH/CRITICAL findings;
- Syft/Trivy version output.

The scan step is blocking for any HIGH/CRITICAL result, including unfixed
findings, but the upload step uses `if: always()` so failure evidence remains
available. This artifact proves only that CI run and its local image IDs. It is
not a published or signed release.

All third-party GitHub Actions are pinned to immutable commit SHAs with their
reviewed tag recorded as a comment. Updating a tag requires reviewing and
changing the SHA.

## Protected release evidence

Only an immutable `vMAJOR.MINOR.PATCH` tag can enter the `release` job. The job
also targets the GitHub `production-release` environment. Repository owners
must configure that environment with required reviewers and prevent
self-review; until then, signing is `NO-GO` even though the workflow is
executable.

The release job:

1. pushes backend/frontend images to GHCR by digest;
2. pulls those exact digests, scans them with Trivy, and runs the production
   TLS/setup/Playwright topology against the same immutable references;
3. asks BuildKit for OCI SBOM and `mode=max` provenance;
4. creates GitHub build-provenance attestations for each digest;
5. uses Cosign 3.1.1 keyless OIDC signing on each immutable digest;
6. verifies the workflow certificate identity and uploads the verification
   JSON plus tag/commit/workflow/digest manifest.

Tag, commit, GitHub artifact, OCI attestation and GHCR digest must all agree.
No release evidence may contain a session secret, TLS key, setup token or LLM
API key.

Production startup is supported only through
`scripts/deploy-production.sh`. It rejects mutable tags and performs
`cosign verify` plus SLSA-provenance and SPDX-SBOM attestation verification for
both image digests before invoking Compose. A raw `docker compose up` is an
explicit security bypass and is not an accepted installation path.

## Local remediation evidence boundary

Observed locally on 2026-07-10:

- host: macOS 26.4, Darwin 25.4.0, arm64;
- Docker Engine client/server 27.4.0;
- Docker Compose 2.31.0-desktop.2;
- Google Chrome 150.0.7871.115 and Safari 26.4.

The remediation build produced local Linux/arm64 image IDs only:

- backend: `sha256:862c90ff2b2057ba058e19dc01c4bff38c240210ea65e7fa4689d7d7d6f48c82`;
- frontend: `sha256:38bf291b7c5de3b074be7d3dcee02c50e030d4e6144555041ed1a07d64dd4ec1`.

`scripts/test-production-compose.sh` passed setup enrollment, readiness,
post-enrollment setup-token rejection, token removal/restart, TLS headers and
the Compose/runtime JSON topology allowlists. With
`PLAYWRIGHT_BROWSER_CHANNEL=chrome`, all three production-topology Playwright
tests passed against the running TLS endpoint, including same-origin liveness,
version, preflight, CSRF, real login and disabled-capability display. The Docker build contexts observed were
approximately 419 KiB (backend) and 272 KiB (frontend).

These local image IDs are not registry digests and are not signed artifacts.
This machine is outside the Ubuntu x86_64 production matrix. Local Compose
runtime can prove topology invariants and product behavior, but cannot validate
the supported OS, filesystem, Engine candidate lines, clean installation,
upgrade, rollback, SBOM/signature publication or production SLO.
